# Интеграция лаборатории нейронных сетей как практической работы AI-edu

Дата: 14 ноября 2026 года.

## 1. Что нужно сделать

Добавить **«Виртуальную лабораторию нейронных сетей»** в существующий каталог практических работ рядом с мастерской генерации лекции, конструктором практического занятия и педагогическим конструктором.

Администратор выбирает лабораторию при настройке учебного элемента `PRACTICE`, задаёт инструкцию и критерии, сохраняет черновик и публикует работу. Студент открывает её внутри AI-edu, выполняет эксперимент, сохраняет результат, проходит самопроверку и сдаёт работу. Прогресс обновляет сервер через существующий Practice Engine.

Лаборатория получает собственный инструмент выполнения. Общие этапы остаются такими же, как у остальных практик:

```text
Курс → Модуль → Практическая работа
                    ↓
             Задание и критерии
                    ↓
       Лаборатория нейронных сетей
                    ↓
           Результат и самопроверка
                    ↓
          Сдача и обновление прогресса
```

Это инструкция по будущей реализации. Точки подключения проверены по текущему коду AI-edu. Исходники NN 3D Viz Lab в этой проверке не изучались: её функции известны по документу «ТЕХНИЧЕСКАЯ НОВИЗНА.docx». Формат экспорта, стек и команды сборки лаборатории нужно установить на первом этапе. Числа «32 пространства» и «7 визуализаторов» до проверки исходников считать описанием из документа.

## 3. Новый тип практики

Предлагаемые идентификаторы:

```text
practice_type: nn3d_lab
plugin_version: 1.0.0
name: Виртуальная лаборатория нейронных сетей
frontend_editor: nn3d_lab
student_runtime: nn3d_lab
grading: self_assessment
```

### Backend

Создать `apps/activities/nn3d/plugin.py` и зарегистрировать плагин в `apps/activities/registry.py`.

Плагин реализует существующие методы: `validate_config`, `materialize_config`, `evaluate`. Для создания критериев и вычисления самооценки использовать `ChecklistPlugin`.

Общие поля `instructions`, `criteria`, `source_url`, `source_files` проверять существующей проверкой задания. Специальные настройки лаборатории проверять отдельно. Сейчас `assignment.py` отклоняет неизвестные ключи: при делегировании передавать ему только общие поля, предварительно проверив полный список разрешённых ключей нового конфига. Не ослаблять проверку остальных практик.

**Важно:** лаборатория использует общий жизненный цикл практики, но её данные — состояние эксперимента. Не добавлять её в `CONSTRUCTORS` как генератор учебного текста. Не задавать `workspace_type` только ради похожего интерфейса: в `services.submit()` этот атрибут включает подготовку ответа через API документов генератора. Для лаборатории нужен собственный обработчик сохранения и подготовки результата.

### Frontend

Создать:

- `src/practice/nn3d/Nn3dLabRuntime.tsx` — выполнение работы;
- `src/practice/nn3d/Nn3dLabConfigEditor.tsx` — общий редактор задания плюс настройки лаборатории;
- `src/practice/nn3d/api.ts` — сохранение и загрузка эксперимента;
- `src/practice/nn3d/bridge.ts` — обмен с приложением лаборатории.

Зарегистрировать плагин в `src/practice/registry.ts`. В `commonTask.ts` добавить `nn3d_lab` к практикам с общим заданием: тогда инструкция и критерии сохранятся при переключении инструмента. Настройки самой лаборатории при переключении заполняются её начальными значениями.

В `PracticeFlow.tsx` название инструмента сейчас берётся из `workshopFor()`. Добавить для нового плагина корректное отображаемое название через общие метаданные плагина или манифест.

Использовать существующий `RuntimeProps`: `onBackToTask` для возврата к заданию, `onDraftChange` для локального черновика и `onActivityChange` для блокировки сдачи во время вычислений/сохранения. После успешного сохранения вызывать `onReview({ experiment_revision }, { title })`. Критерии добавляет общий экран самопроверки; окончательную отправку выполняет `PracticeRunner`.

### Полноэкранный режим

В текущем `PracticeFlow.tsx` значение `layout: 'workspace'` одновременно:

- включает широкий интерфейс инструмента;
- включает загрузку документов и сообщений генератора на самопроверке;
- добавляет `completed: true` в сдаваемые данные.

Перед подключением лаборатории разделить эти назначения. Например, оставить `layout` для внешнего вида, а отдельный признак `resultKind: 'workspace_document' | 'nn3d_experiment'` использовать для загрузки и показа результата. Это новый предлагаемый контракт; сейчас такого поля нет.

Существующим генераторам явно назначить прежнее поведение. Лаборатория открывается в широком интерфейсе, но обращается к своему API состояния. Общая кнопка сдачи передаёт согласованный payload нового плагина. Проверки обязательности отчёта также распространить на лабораторию: сейчас часть этих проверок привязана к `guided_assignment`.

## 4. Как встроить саму лабораторию

Для первой версии предлагается сохранить лабораторию отдельной собираемой частью и открывать её в `iframe` внутри `Nn3dLabRuntime`. Это позволяет подключить существующее приложение без переноса вычислительного ядра в React-компоненты платформы.

После проверки исходников добавить режим `embed`:

1. Убрать внешнее меню и дублирующую навигацию лаборатории.
2. Реализовать загрузку и экспорт состояния через небольшой адаптер.
3. Передавать события готовности, изменения состояния, завершения расчёта и ошибки.
4. Поддержать остановку расчёта и освобождение ресурсов при закрытии инструмента.
5. В режиме просмотра результата блокировать изменения и запуск нового обучения.

Сборку размещать по фиксированному версионированному пути, например `/labs/nn3d/<release>/index.html`. Это планируемый путь, сейчас он не настроен. Релиз выбирается из серверного списка разрешённых сборок; произвольный URL в настройках задания не нужен. В конфигурации опубликованной практики закрепить релиз, чтобы обновление лаборатории не ломало старые попытки.

Проверить base path, загрузку JS, моделей, worker/WASM и обновление страницы в dev и production. В `AI-edu-frontend/server.mjs` статика раздаётся из `dist`, поэтому каталог лаборатории должен попадать в итоговый образ. HTML лаборатории должен проверять обновления; неизменяемые ресурсы можно кешировать по версии. Старые сборки сохраняются, пока на них ссылаются задания.

Для встроенной доверенной сборки на одном origin iframe не является отдельной границей доступа. Все проверки прав выполняются в backend AI-edu. Cookies, CSRF, сохранение и сдачу обрабатывает родительский интерфейс; лаборатории не требуется собственная авторизация.

### Минимальный протокол обмена

Следующие сообщения предлагается реализовать в адаптере обеих сторон:

| Направление | Событие | Содержимое |
| --- | --- | --- |
| Лаборатория → AI-edu | `nn3d.ready` | Поддерживаемая версия протокола |
| AI-edu → лаборатория | `nn3d.init` | ID сессии обмена, язык, режим, настройки, сохранённое состояние |
| Лаборатория → AI-edu | `nn3d.state_changed` | Состояние и краткие результаты для автосохранения |
| AI-edu → лаборатория | `nn3d.export_request` | ID запроса на получение актуального состояния |
| Лаборатория → AI-edu | `nn3d.export_result` | ID запроса, состояние и сводка эксперимента |
| AI-edu → лаборатория | `nn3d.stop` | Запрос остановки вычислений |
| Лаборатория → AI-edu | `nn3d.error` | Код и понятное сообщение ошибки |

Использовать `postMessage` с точным `targetOrigin`. На приёме проверять `event.origin`, `event.source === iframe.contentWindow` на стороне AI-edu и источник родителя на стороне лаборатории. После инициализации проверять также ID сессии, версию протокола и структуру payload. Обработчики снимать при размонтировании. Предусмотреть таймаут готовности и повторную инициализацию после перезагрузки iframe.

Событие завершения расчёта обновляет результат эксперимента. Сдача выполняется отдельной кнопкой AI-edu после самопроверки.

Общая часть конфигурации остаётся совместимой с текущим редактором. Добавляется объект `lab`:

```json
{

  "plugin_version": "1.0.0",
  "title": "Исследование полносвязной нейронной сети",
  "description": "Выполните эксперимент и объясните полученные результаты.",
  "config": {
    "instructions": ["{\"type\":\"doc\",\"content\":[{\"type\":\"paragraph\",\"content\":[{\"type\":\"text\",\"text\":\"Запустите эксперимент, измените один параметр сети и сравните результаты.\"}]}]}"],
    "criteria": [
      {"title": "Эксперимент выполнен", "description": "Сохранены параметры и результат расчёта.", "is_required": true},
      {"title": "Результаты сравнены", "description": "Объяснено влияние изменённого параметра.", "is_required": true}

    "lab": {
      "release": "nn3d-1",
      "preset_id": "mlp-basic",
      "allow_architecture_edit": true

```

`nn3d-1` и `mlp-basic` — условные идентификаторы примера. Перед реализацией сопоставить их с проверенной сборкой и реальным пресетом. После добавления плагина payload отправляется существующим `PUT /api/v1/items/{short_id}/practice/draft/`, публикация — `POST` на тот же адрес.

`instructions` — массив строк с JSON-документами Tiptap, как в текущей платформе. `source_url` и `source_files` при необходимости работают по существующему контракту; не использовать `source_url` как адрес приложения лаборатории.

## 6. Сохранение эксперимента и сдача

Локальное IndexedDB лаборатории полезно для черновика, но для восстановления на другом устройстве и сохранения результата попытки нужно серверное состояние.

Предлагается новая модель `NnLabExperiment`: связь один-к-одному с `PracticeSubmission`, `schema_version`, `revision`, `state`, `summary`, `report`, `updated_at`. Владелец и версия задания определяются через попытку. Для модели нужна миграция.

Содержимое `state` определить по реальному экспорту лаборатории: архитектура/граф, веса, смещения, входы, параметры обучения и данные, необходимые для восстановления выбранного эксперимента. `summary` содержит краткие результаты запусков. Формат проверяется на сервере по версии схемы. Если эксперимент использует случайность, сохранять seed и итоговые параметры; обещание точного повторения обучения проверять отдельно.

Для MVP выбрать небольшой встроенный набор данных. Загрузка больших пользовательских наборов — отдельное расширение. Сначала установить лимиты JSON и массивов по реальным пресетам; стартовый ориентир — до 1 МиБ на снимок и до 500 точек на кривую. Сервер отклоняет превышение лимита с понятной ошибкой. Проверять размеры матриц, разрешённые типы блоков, глубину графа и конечность чисел. Экспорт JSON должен явно преобразовывать typed arrays в согласованный формат.

### Предлагаемый новый API

Этих endpoints сейчас нет; их нужно добавить в `config/urls.py` и новые views/services лаборатории.

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/v1/items/{short_id}/practice/nn3d/{submission_id}/` | Загрузить состояние своей попытки; до первого сохранения вернуть пустое состояние и `revision: 0` |
| `PUT /api/v1/items/{short_id}/practice/nn3d/{submission_id}/` | Создать или обновить состояние с проверкой текущей ревизии |

Пример тела сохранения после согласования схемы:

```json
{
  "revision": 0,
  "schema_version": 1,
  "state": {},
  "summary": {},
  "report": "Я изменил параметр сети, сравнил результаты и описал наблюдаемые различия."
}
```

Пустые `state` и `summary` здесь обозначают место для данных согласованной схемы. Они не являются достаточным результатом для сдачи. Успешный ответ возвращает сохранённые данные и увеличенную ревизию; устаревшая ревизия даёт `409`.

При каждом запросе проверять авторизацию, принадлежность попытки пользователю и учебному элементу, доступ к модулю, тип `nn3d_lab` и закреплённую версию. CSRF для записи — по текущим правилам платформы. Запись разрешена только при `IN_PROGRESS`; сданное состояние доступно владельцу для чтения.

Автосохранение выполнять с задержкой после изменений, с одним активным запросом и очередью последнего состояния. Перед самопроверкой остановить вычисления, запросить актуальный экспорт и дождаться успешного сохранения. При ошибке показать повтор сохранения и оставить работу открытой. Результат сдачи не должен зависеть только от `sessionStorage`.

### Финальная сдача

Использовать существующий endpoint:

```text
POST /api/v1/items/{short_id}/practice/
```

Предлагаемый payload нового типа:

```json
{
  "submission_id": 123,
  "submission_data": {
    "experiment_revision": 7,
    "checks": [true, true]
  }
}
```

Внутри существующей транзакции `submit()` добавить подготовку результата для лаборатории: получить состояние именно этой попытки, проверить ревизию, валидность результата и отчёт от 40 до 20000 символов. Снимок эксперимента и отчёт присоединять из серверного состояния; затем вызывать оценивание плагина. Для блокировок соблюдать существующий порядок: пользователь → попытка → эксперимент. Обновление состояния использует тот же порядок, чтобы сохранение не прошло одновременно с окончательной сдачей.

В `PracticeSubmission.submission_data` зафиксировать снимок, отчёт, ревизию и критерии. Плагин проверяет снимок и обязательные критерии, а сервер создаёт `PracticeResult` и обновляет прогресс существующим механизмом. Результаты браузерного расчёта сохраняются как данные работы обучающегося; это не независимая проверка правильности вычислений.

Повтор идентичного запроса сдачи должен вернуть прежний результат. Для этого до добавления серверного снимка сравнивать повтор с исходным клиентским payload, сохранённым в составе результата, либо с его нормализованным представлением. Различающийся запрос к сданной попытке отклонять. Текущая ветка для обычных плагинов сравнивает `saved_data == data`; после обогащения снимком одного этого сравнения недостаточно. Существующие типы практик сохраняют своё поведение.

Для MVP использовать `grading_source = SELF_ASSESSMENT`: Ψ вычисляется по критериям, все обязательные должны быть подтверждены. `automatic_score` и `teacher_score` остаются пустыми. После успешной сдачи общий механизм отмечает практику выполненной. Запуск симуляции сам по себе не завершает работу.

## 7. Что увидит студент

1. **Задание.** Название, инструкция, вложения, критерии и кнопка начала.
2. **Выполнение.** Лаборатория внутри страницы, параметры сети, визуализация, запуск/остановка, статус сохранения и поле короткого отчёта.
3. **Самопроверка.** Краткая сводка эксперимента, отчёт, критерии и кнопка завершения.
4. **После сдачи.** Сохранённый результат и эксперимент в режиме чтения.

Новая попытка создаёт собственное состояние. Публикация нового задания не меняет конфигурацию, релиз лаборатории и результаты уже начатой попытки. Ключ локального кеша включает пользователя, учебный элемент, версию и попытку; при смене аккаунта состояние предыдущего пользователя не загружается.

Режимы «демонстрация» и «полноценный расчёт» обозначать согласно возможностям конкретного пресета. Для MVP выбрать один проверенный вычислительный пресет; остальные подключать после проверки экспорта, восстановления и расчётов.

AI-тьютор может продолжать помогать по общей инструкции и отчёту. Текущий `practice_context()` уже читает отчёт из `submission_data`. При расширении контекста текущим экспериментом передавать только ограниченную сводку собственной попытки; матрицы и наборы данных целиком не нужны. Отдельный AI-генератор и workspace worker лаборатории для MVP не требуются.

## 8. Порядок работ и критерии приёмки

| Этап | Проверяемый результат |
| --- | --- |
| 1. Аудит лаборатории | Установлены команды сборки, вычислительный пресет, формат состояния и способ восстановления |
| 2. Контракты | Согласованы конфигурация, схема состояния, протокол iframe и payload сдачи |
| 3. Backend | Новый тип появляется в API каталога; работают публикация, сохранение, права, ревизии и сдача |
| 4. Адаптер лаборатории | Работают embed, загрузка/экспорт состояния, остановка и режим чтения |
| 5. Frontend | Карточка доступна в редакторе, работают три этапа и серверное восстановление |
| 6. Приёмка | Полный сценарий пройден на тестовом окружении, прежние практики работают |

Проверить следующие сценарии:

- Администратор публикует `nn3d_lab`; студент видит её в своём модуле.
- После эксперимента и перезагрузки восстанавливаются параметры, результаты и отчёт; на другом устройстве загружается серверная версия.
- Пустой/некорректный эксперимент, устаревшая ревизия или неподтверждённый обязательный критерий блокируют сдачу на сервере.
- Два сохранения и параллельная сдача не перезаписывают более новое или уже сданное состояние.
- Чужой пользователь и пользователь без доступа к модулю не могут читать, менять или сдавать попытку.
- Повтор запроса сдачи не создаёт второй результат и не меняет снимок.
- После сдачи состояние неизменно; новая публикация не меняет начатую попытку.
- Ошибки iframe, таймаут экспорта, прерванное сохранение и отсутствие поддержки 3D показывают понятное сообщение с возможностью повторить действие.
- Генерация лекции, конструкторы и `guided_assignment` проходят прежние сценарии; лаборатория не вызывает API AI-документов.
- Статика лаборатории работает в production-сборке, включая прямую загрузку её HTML и ресурсов.

Существующие проверки для регрессии, выполнять в настроенном тестовом окружении:

```powershell
# Из AI-edu-backend
python manage.py check
python manage.py test apps.activities --settings=config.settings_test --noinput

# Из AI-edu-frontend
npm test
npm run build
```

Добавить отдельные backend-тесты нового типа, тесты протокола обмена и один браузерный сценарий: публикация → эксперимент → сохранение → перезагрузка → самопроверка → сдача. Отдельно проверить блокировки на PostgreSQL. Команду проверки самой лаборатории брать из её `package.json` после аудита. Перечисленные проверки в рамках подготовки этой инструкции не запускались.

## 9. Короткие промпты для реализации

Передавать промпты последовательно. Разработчику/агенту нужен доступ к обоим репозиториям AI-edu, исходникам лаборатории и этому файлу. Если лаборатории ещё нет в рабочей папке, сначала предоставить её репозиторий или архив. В каждом промпте «инструкция» означает `AI-edu-backend/docs/nn3d-integration.md`.

### Промпт 1 — проверить лабораторию

```text
Прочитай инструкцию интеграции nn3d-integration.md и исходники NN 3D Viz Lab.
Установи стек, команды сборки, реальный вычислительный пресет и формат экспорта.
Проверь сохранение и восстановление эксперимента. Зафиксируй схему состояния,
релиз и минимальный embed-адаптер. Если исходников нет, укажи, чего не хватает.
```

### Промпт 2 — зарегистрировать тип практики

```text
По инструкции добавь backend-плагин nn3d_lab@1.0.0 в PracticeRegistry.
Переиспользуй общие инструкцию, критерии и SELF_ASSESSMENT; проверь lab-настройки.
Сохрани существующий цикл черновик → публикация → закреплённая попытка.
Не включай обработку workspace-документов. Добавь тесты регистрации и публикации.
```

### Промпт 3 — сохранить состояние и результат

```text
По согласованной схеме добавь модель и API эксперимента для попытки nn3d_lab.
Реализуй права, ревизии, лимиты, восстановление и запрет записи после сдачи.
Подключи серверный снимок к submit(), проверку отчёта и обязательных критериев.
Обеспечь повторяемую сдачу и защиту от гонок сохранения. Добавь backend-тесты.
```

### Промпт 4 — подготовить лабораторию к встраиванию

```text
Добавь в NN 3D Viz Lab режим embed и протокол обмена из инструкции.
Реализуй init, экспорт состояния, события изменений, ошибки, stop и read-only.
Проверь origin/source, ID сессии и схемы сообщений. Сохрани математическое ядро.
Собери лабораторию для версионированного пути и проверь восстановление пресета.
```

### Промпт 5 — подключить интерфейс практики

```text
Зарегистрируй frontend-плагин nn3d_lab@1.0.0 и его редактор/StudentRuntime.
Встрой лабораторию в общий сценарий задания, выполнения и самопроверки.
Раздели широкий layout и работу с документами генератора в PracticeFlow.
Обнови hasCommonTask и название инструмента, сохрани поведение прежних практик.
```

### Промпт 6 — соединить лабораторию с сохранением и сдачей

```text
Соедини nn3d runtime, bridge и серверное API эксперимента по инструкции.
Добавь автосохранение, восстановление, отчёт и ожидание сохранения перед review.
Передавай experiment_revision и checks в общий endpoint сдачи, покажи снимок
после завершения. Обработай 409, ошибки iframe и сохранения. Добавь UI-тесты.
```

### Промпт 7 — проверить интеграцию целиком

```text
Проверь nn3d_lab по критериям приёмки инструкции на тестовом окружении.
Пройди публикацию, эксперимент, перезагрузку, восстановление и повторную сдачу.
Проверь чужой доступ, гонки, старые версии и регрессию существующих практик.
Запусти backend-тесты, frontend-тесты и сборку; исправь ошибки и дай краткий отчёт.
```

### Промпт 8 — подготовить поставку

```text
Подготовь поставку интеграции nn3d_lab: миграции, версионированную сборку
лаборатории, изменения Docker/build и инструкцию запуска на тестовом окружении.
Проверь base path, worker/WASM и сохранение сборок для старых попыток.
Перечисли изменённые файлы, результаты проверок и оставшиеся ограничения.
```

## 10. Границы первой версии

Первая версия включает один проверенный пресет, общий каталог практик, встроенный инструмент, серверное сохранение и восстановление, отчёт, самопроверку и прогресс. Расширение каталога моделей, большие наборы данных и независимое автоматическое оценивание можно добавлять следующим этапом после работающего полного сценария.
